# AI-Ready PRD 结构约定

编写图文 PRD 时使用本结构。文件与一级标题使用具体需求名称，命名与覆盖规则遵循 SKILL.md。PRD 面向中文产品、设计和研发协作，也会交给实现 AI 使用，因此必须范围清晰、规则明确、证据可追溯、可直接执行。原型截图已经承载界面信息，PRD 不要重复描述明显 UI。

适用 Skill 版本：1.2。保留以下章节顺序、标题、截图与表格格式；示例维度是选用提示，不是待填清单。简单需求用短句和单层列表，按需省略可选小节。

## 输出结构

````markdown
# {需求名称}

> 页面: {page_id} | 版本: {version} | 添加时间：{yyyy-MM-dd HH:mm:ss}


## 1. 需求概览

### 1.1 需求说明

[只用一句话概括整个需求的对象、变化和目标。全文只在此处写一次，不按功能、小点或用例分别说明需求。]

### 1.2 需求范围

- 需求范围: [以用户本轮触发 skill 时说明的范围为准；结合 annotations.json 标注和源码证据说明本次要写哪些功能用例。不要机械地只写标注内容，也不要无依据扩散到无关功能；用无序列表呈现，一个功能一条。]

## 2. 详细功能需求

### 2.{n} {功能名称}

**功能截图：**
![{功能名称}](prd-assets/{feature-image}.png)

[复杂功能的流程图按 SKILL.md 的规则放在此处，跨功能主流程放在需求范围之后；无图时删除占位。]

**功能规则**:

[只写影响业务逻辑的条件与结果，如计算口径、权限、优先级、互斥、联动、持久化或异常处理。不写界面和交互描述。简单逻辑使用短句或单层短列表，复杂条件才用小表格或矩阵；没有额外业务逻辑时省略本小节，不为凑内容复述 Demo。]

**规则细化（可选）**:
[仅当主规则结构无法表达清楚时补充，例如计算公式、排序口径、状态机、权限矩阵或跨功能联动。优先使用小表格、判断矩阵或极短列表，避免长段落。]

**边界与异常**:
[仅补主规则未表达、影响实现的特殊边界或异常；常规行为不展开。没有依据且影响实现的决定列入“待确认”。无新增信息时省略本小节。]

**数据要求（可选）**:

| 字段 | 类型 | 必填 | 默认值 | 说明 |
| ---- | ---- | ---- | ------ | ---- |
| 中文字段名（必要时补充技术字段：xxx） | 文本/数字/布尔/列表/对象 | 是/否 | ... | ... |

**补充说明（可选）**:
[只在有助于实现或理解规则时补充。]

## 3. 待确认（没有未决事项时删除）

- [具体缺少的产品决定及影响，不把推测写成结论。]
````

## 写作规则

- 最终 PRD 正文必须优先使用中文。除文件路径、图片链接、必要字段名、命令示例和无法翻译的产品专名外，能用中文表达的地方都用中文。
- 源码中的英文变量、函数、枚举、CSS 类名、DOM 属性名只作为理解证据，不要原样写入正文。
- 正文只描述本次要实现的功能、规则和结果；需求范围只列要实现的内容，省略范围排除、非目标、未覆盖或暂不支持的无关能力说明。必要的权限、互斥、限制和异常规则用明确的触发条件、系统处理与结果表达。
- “需求说明”仅在需求概览中写一次，用一句话说明整个需求；详细功能下不再重复设置该字段。
- 功能规则只描述影响业务逻辑的条件与结果。例如“字号变化后重新计算分页，阅读位置保持在原正文内容”属于业务规则；“点击字号按钮打开设置面板”属于交互描述，应删除。
- 简单功能用短句或单层短列表，不增加子标题、多层编号或嵌套列表；复杂条件或组合关系才用小表格或矩阵。
- 每条规则应尽量原子化，包含明确条件、系统处理和结果影响。避免“支持设置”“保持一致”“进行校验”“展示对应内容”这类缺少条件和结果的空泛表述。
- 规则细化只用于补充复杂逻辑，不要重复主规则内容；没有复杂公式、状态机、权限矩阵或跨功能联动时直接省略。
- 只撰写当前迭代范围。用户本轮说明的范围优先；`annotations.json` 用于理解业务意图、重点区域、遗漏状态和截图目标，不是唯一范围边界。
- 标注用于辅助判断范围和理解业务意图，不要照抄标注文案。用户明确要求的未标注功能可以写；与本轮范围无关的标注不要强行写入。
- 界面和交互由 Demo 与截图承载；不写布局、颜色、间距、控件、操作步骤、弹窗开合、跳转路径、提示文案或视觉状态。业务状态迁移和跨功能联动仍应写成必要逻辑规则。
- 每个需求用例先确定“截图目标状态”，再截图，再写功能规则。
- 不设置“交互与状态补充”小节，也不把界面或交互描述转移到边界异常、补充说明等其他小节。
- 仅在有助于实现时包含源码相关内容引用；尽量提取算法规则，而不是引用源码。
- 标注信息只能作为理解输入，不要原样罗列。按功能归纳为必要规则，仅补影响实现的信息。

- 默认逐功能附真实状态截图，截图失败时在对应功能写明原因；不使用概览或标注红框图替代。
- 默认写短，读者已有 Demo 和业务上下文；省略已可见的操作、通用背景和重复解释，保留影响实现的决定。简单需求以一句总体需求说明、截图和几条业务逻辑规则讲清，不逐项展开模板维度。
- 仅当简短文字难以讲清复杂关系且图能减少阅读量时，才使用 Markdown 的 `mermaid` 围栏代码块；沿用 SKILL.md 的插入规则，同一图只保留一次，不在正文逐节点复述。
