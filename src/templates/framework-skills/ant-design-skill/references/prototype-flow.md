# Prototype Scope & Page Flow

## 1. 核心原则

原型的页面数量由产品表达需要决定，而不是固定为 1 页。

目标：**用最少且足够的页面，完整表达核心用户任务。**

## 2. 单页优先的情况

以下情况通常不需要拆页：

- 列表 + 简单新建 / 编辑，可以用 Drawer 完成
- 详情只需要少量字段预览，可以用 Modal / Drawer
- 配置只有少量开关或参数，可嵌入对象详情
- 用户只需要展示一个独立看板、分析结果或工作台

## 3. 应主动拆页的信号

出现任意一项时，优先考虑多页面：

1. **主任务发生变化**：从“找对象”变成“理解对象”再变成“配置对象”。
2. **信息密度过高**：详情内容超过一个 Drawer 能舒适承载的范围。
3. **操作风险或复杂度高**：创建 / 编辑需要多分组表单、步骤或独立上下文。
4. **页面视觉主角冲突**：列表、详情、配置都想成为页面核心。
5. **Tab 开始承担页面级导航职责**：为了不拆页而堆 4～6 个大 Tab。
6. **流程阶段差异明显**：如任务列表 → 任务执行工作台 → 分析结果。
7. **不同角色 / 模式差异明显**：例如运营管理页与审核处理页。

## 4. 常见页面流

### CRUD 管理

```text
数据管理页
  ├─ 新建 / 编辑页（复杂时）
  └─ 对象详情页
       └─ 配置页（配置复杂时）
```

简单编辑仍可用 Drawer，不必机械拆页。

### 项目 / 任务型产品

```text
项目列表
→ 项目工作台
→ 分析结果 / 详情
→ 设置 / 配置（按需）
```

### 审批 / 风控

```text
待办列表
→ 审批处理页
→ 对象详情 / 证据详情（按需）
```

### AI / Agent 产品

```text
任务 / 会话列表（可选）
→ AI Workspace
→ 结果详情 / 报告
→ Agent 设置（按需）
```

## 5. 页面数量控制

- 没有固定上限。
- 通常先规划 1～4 个核心页面；只有产品意图确实需要时再增加。
- 每新增一个页面，都要回答：“这个页面是否承载了一个独立用户任务或明显不同的信息架构？”
- 如果答案是否定的，优先合并回现有页面。

## 6. 页面之间的关系

多页原型至少表达：

- 从哪里进入
- 点击什么进入下一页
- 如何返回
- 当前对象 / 项目上下文是什么

不要求：

- production Router
- 权限系统
- URL 同步
- 浏览器历史完整正确

## 7. 模板使用

一个原型可以重复使用 `scripts/pages/` 中不同模板：

```text
01-DataManagementPage
→ 02-ObjectDetailPage
→ 05-SettingsPage
```

必要时也可以基于最接近的模板新增页面，不受现有 6 个页面模板限制。
