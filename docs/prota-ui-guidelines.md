# Prota 产品 UI 规范（v1.0）

> 适用范围：Prota **产品自身**的项目首页、模板/Skill 管理、Agent 工作台、设置、PRD、分享、流程图与无限画布编辑器。维护日期：2026-11-10。
>
> 这是后续新功能、UI 迭代和 AI 自审的**目标规范**，不是宣称现有代码已经全部符合。当前实现差异与证据见 [`prota-ui-audit-2026-11-10.md`](./prota-ui-audit-2026-11-10.md)。

## 0. 先划清边界与优先级

1. **产品 Chrome**：Prota 的导航、面板、菜单、设置、画布编辑工具等必须遵守本规范；新增产品功能不得自行发明另一套视觉语言。
2. **用户业务 Demo / 画板**：`src/pages/{project_id}/...`、无限画布内部 `boards/{board_id}/`、移动/Web/自由画布模板与 `src/templates/design-systems/` 的品牌风格**不受本规范强制配色和组件约束**。它们应根据业务、用户明确选择的设计系统和页面目标自主设计。产品 UI 与业务页面继续由 iframe 和资源路径隔离。
3. **第三方编辑器**：draw.io / mindmap 的原生画布、图形与文档色彩保持独立；仅其工具栏、弹窗、菜单等宿主外壳向 Prota 视觉对齐。禁止为了统一而污染内容画布。
4. **优先级**：用户本次明确要求 > 数据安全与可用性 > 本规范 > 旧模块局部样式 > 泛用的 `frontend-design` / taste 类生成指导。偏离规范须在改动说明中解释场景、影响及例外范围。
5. **版本隔离**：产品上层 UI 的修改应在共享产品层生效；不得通过批量改写历史 `v1/v2` 或各画板业务源码来统一 UI。遵守根目录 `AGENTS.md` 的工作区、版本、分享与独立运行要求。

## 1. Prota 的视觉性格

**关键词：克制、精密、轻盈、可靠、内容优先。** 它是给产品经理使用的创作工具，不是营销落地页，也不是带重装饰的 SaaS 控制台。

- 浅色、中性、低噪声；紫蓝色只标记关键动作、当前选择、焦点与少量状态。
- 内容与画布是主角；工具是辅助层。优先使用必要时出现的悬浮/上下文工具，避免为一个小功能增加常驻侧栏、第三层导航或重复工具栏。
- 使用空间、对齐、字重和状态来说明层级。**删除没有决策价值的副标题、解释性小字、重复标签和装饰性图标**（延续 `AGENTS.md` 第 9 节）。
- 默认信息密度中等偏紧凑，但不能以 10px 小字、极小点击区域或把操作藏得不可发现为代价。
- 一屏一个清晰的主要目标；非必要不使用大面积渐变、发光、玻璃叠层、厚重阴影、拟物卡片、无意义的动效。
- 优先复用已有产品交互模式；新组件出现前先证明旧组件无法满足需求。

**设计判断三问**：用户现在最想做什么？最重要的操作能否在 3 秒内定位？删除一半次要视觉元素会不会更清楚？

## 2. 设计 Token：目标值与落地方式

### 2.1 颜色（产品层）

| 语义 | 目标值 | 使用边界 |
| --- | --- | --- |
| Workspace 背景 | `#F8F9FB` | 首页、工作台外围背景，延续 `--bg-main` |
| Surface / 弹层 | `#FFFFFF` | 卡片、菜单、对话框与面板，延续 `--bg-sidebar` |
| 主文字 | `#1A1D24` | 标题、正文与操作，延续 `--text-primary` |
| 次级文字 | `#6B7280` | 元数据、辅助说明，延续 `--text-secondary` |
| 边线 | `#E5E7EB` | 输入框、容器、分隔线，延续 `--border` |
| 主强调 | `#6366F1` | 主要 CTA、选中、焦点，延续 `--accent` |
| 强调 Hover | `#4F46E5` | 主按钮悬停/按下，主界面已有使用 |
| 强调浅底 | `rgba(99,102,241,.10)` | 轻选中、Hover，延续 `--accent-glow` |
| 危险 | `#DC2626` | 删除/不可逆操作，只用于危险语义 |
| 成功 | `#16845C` | 成功反馈；不要用绿色代替主 CTA |
| 警告 | `#B45309` | 风险、待处理；新语义建议值，未全局落地 |

- **先复用** `portal/shell.css` 的根变量；不要在新增模块重写 `#6254D9`、`#5765CE`、`#1F2937` 等“另一套品牌主色”。无限画布现有 `--accent:#5765ce` 是**待迁移的历史实现**，不是新功能应照抄的标准。
- 未来重构可在产品层增加 `--ui-*` 语义别名（如 `--ui-surface: var(--bg-sidebar)`），逐模块替换；**本规范不表示这些别名今天已存在**。
- 色彩不仅靠颜色区分：选中应有背景/边框/标记，错误须有文字，禁用须有语义与视觉反馈。
- 文本与背景的常规对比度目标 ≥ 4.5:1，较大文字 ≥ 3:1；次级文字不能为了“高级灰”牺牲可读性。数据化检查以实际渲染结果为准。

### 2.2 字体与排版

- 正文首选现有 `Inter, -apple-system, BlinkMacSystemFont, "Segoe UI", "PingFang SC", "Microsoft YaHei", sans-serif`；`Outfit` 仅用于品牌、少量关键标题/数字，不要一个页面随意混用三种字体。
- 默认正文 13–14px，行高 1.45–1.6。建议层级：页面主标题 20–24px / 600；弹窗标题 18–20px / 600；区块标题 15–16px / 600；正文 13–14px / 400–500；辅助说明 12px；极少量非关键元数据 11px。**不得为密度再新增 10px 甚至更小的常规文本。**
- 字重优先 400 / 500 / 600。不要通过连续加粗每行标题和标签制造层级。英文短标签与数字使用正常字距，中文正文避免全大写/过度字间距。
- 长项目名、模型 ID 和路径应有 `min-width:0`，可换行或省略并能查看完整内容；不可直接撑坏布局。中文输入法、混合英数、无空格长串都要验证。

### 2.3 间距、几何与层次

| 项目 | 目标规范 | 说明 |
| --- | --- | --- |
| 间距步长 | `4 / 8 / 12 / 16 / 24 / 32px` | 相邻图标 4–8；控件间 8–12；区块 16–24；页面留白 24–32 |
| 小控件圆角 | `6px` | 标签、小菜单项、图标按钮 |
| 常规控件圆角 | `8px` | 按钮、输入框、选择器 |
| 卡片圆角 | `10px` | 项目/模板/Skill 卡片；禁止同一列表随意混用 8/10/14 |
| 浮层/对话框圆角 | `14px` | Menu / Popover 可为 10px；大型设置窗口可保留 16px 特例 |
| 胶囊 | `999px` | 仅标签、分段指示、悬浮工具条，不让普通按钮全部变成胶囊 |
| 常规按钮高度 | `36px` | 主次动作统一基线；密集工具栏允许 32–34px |
| 输入控件高度 | `38–40px` | 同一表单内高度必须一致 |
| 图标视觉大小 | `16–18px` | 工具栏；图标笔画约 1.75–2px，复用现有 SVG/Lucide 风格 |
| 阴影 | 少、浅、仅浮起时 | 常态靠边界区分；菜单/模态层用一层柔和阴影 |

这些是**新代码基线**，不是要求一次性回写每个旧选择器。已有特例必须基于用途而非开发者个人审美。

## 3. 页面结构与视觉层级

1. **首页（项目/模板/Skill）**：沿用一套顶部筛选/搜索、一套卡片节奏与操作层级；同级卡片的标题、元信息、动作位置对齐；空状态明确下一步。避免卡片内又嵌三层卡片。
2. **工作台**：画布/预览占主要空间；项目、版本、Agent、PRD 入口的层级应可辨认。上下文操作跟随对象和状态，避免与全局操作混淆。
3. **无限画布**：保留“轻量底部创作工具条 + 选中后上下文操作 + 右键菜单/命令面板”的心智模型。默认不新增长驻侧栏，不给画板业务内容注入产品工具样式；每次修改上层工具应对所有使用同版运行时的画板生效。
4. **设置**：单一设置窗口、左侧分类（狭窄时转顶部选择）、右侧编辑与可达的底部操作区。没有必要时不叠加第三列。沿用 `portal/modules/settings/` 的草稿/保存/放弃确认规则。
5. **PRD 与流程图**：文档正文优先；工具区只露常用操作，细节用上下文面板展开。第三方编辑器外壳可贴近 Token，但文档内容与图形样式保持独立。
6. **弹窗**：只用来做确认、集中编辑或打断性任务；普通配置优先在当前面板完成。标题说明“要做什么”，主要操作用动词；取消/次要动作靠前，确认主动作靠后，危险操作显式告知后果。

### 3.1 操作优先级

- 每个工作区/弹窗视觉上**最多一个 primary CTA**。同级次动作使用 secondary/ghost；危险动作不是紫色主操作的变体。
- 图标按钮必须有 `aria-label` 或可访问文本，必要时有 tooltip；禁用时给出原因，不能只降低透明度。
- 首选直接操作与轻量菜单；不要为了“高级感”隐藏核心路径、强迫多次 Hover 或增加无价值的点击。
- 新功能若需要说明教程，先检查是否能简化布局和文案。

## 4. 组件行为契约（不仅看截图）

| 组件 | 必须具备 | 不应出现 |
| --- | --- | --- |
| Button / Icon button | default、hover、active、focus-visible、disabled、loading；点击后及时反馈 | 无状态按钮、图标无名称、重复主 CTA |
| Input / Select / Search | label、placeholder 辅助、焦点、错误说明、长值处理、中文输入法兼容 | 只靠 placeholder 当标签、保存失败清空输入 |
| Menu / Popover | 明确锚点；Esc/外部点击关闭；可键盘抵达；位置不溢出视口 | 多层浮层同时常驻、菜单裁切、关闭时误清空选择 |
| Dialog | 正确 `role` / `aria-modal`；初始焦点、焦点约束、Esc、关闭后焦点返回触发器 | 模态叠模态、遮挡主操作、未经确认丢草稿 |
| Drawer | 可关闭、可滚动；尺寸边界；拖宽后保留内容区可用 | 固定宽度把画布挤没、底部操作被遮挡 |
| Tabs / Segmented | 选中明确；交互与 `aria-selected` / `aria-controls` 同步 | 用纯色差作为唯一选中指示 |
| Toast / Status | 成功、失败、等待有不同语义；错误可读、不过早消失 | 虚假成功、吞错误、纯颜色反馈 |
| Card / Empty / Skeleton | 统一密度、标题层级；空态给行动；加载时稳定布局 | 装饰图标堆砌、页面抖动、卡片高度无规律 |
| Canvas tool | 上下文明确、可撤销、取消不污染状态、选择与内容不丢失 | 工具层覆盖画板 CSS、重复的操作入口 |

**交互一致性**：Esc 从最内层菜单/编辑态开始退出；提交失败保留输入；涉及删除/覆盖/切换未保存内容必须防丢失；完成操作尽量恢复原上下文（选中对象、滚动位置、工作区与焦点）。

## 5. 响应式、无障碍和动效

- 必查桌面 `1440×900`、中间宽度 `1024×768` 和边界宽度 `860×768`；对应有窄屏布局的窗口再查 `390×844`。现有工作台 `--viewport-min-width:440px`，低于此处**不能假定支持完整画布操作**，但模态和可关闭动作仍不得不可达。
- 使用 `min-width:0`、内容溢出处理、`min()/max()/clamp()` 和容器约束；避免按钮排成不可换行的一长排。窗口底部动作在滚动容器外或固定区域可访问。
- 所有功能不应依赖 Hover 才能使用；键盘 Tab 路径清楚，有可见的 `:focus-visible`；纯图标控制要有名称；状态提示用 `role=status/alert` 或适当 `aria-live`。
- 常规控件点击区域不小于 32×32px；触摸布局重要操作争取 ≥40×40px。别把 16px 的图标尺寸误当点击区域。
- Hover / 选中一般 140–180ms；对话框出现不超过约 200ms；避免持续跳动与过多位移动效；尊重 `prefers-reduced-motion`。
- 不得为了 UI 整齐破坏实际业务：自动保存状态、未保存标识、错误提示、历史版本隔离、分享后独立运行必须保留。

## 6. 代码实现规则（新 UI 必须执行）

1. **先检索，后新增**：先检查 `portal/shell.css` / `portal/index.html` 及相关 `portal/modules/**` 的同类组件；能复用则复用。说明新组件为什么必要。
2. **产品 Token 单一来源**：全局主色及通用表面/文字语义引用根变量；局部变量只允许模块专用尺寸或第三方适配。暂不大面积重写旧 CSS，但禁止给新功能增加一整套硬编码配色。
3. **组件用作用域选择器**：新模块使用清晰前缀（如 `.us-`、`.sm-`），禁止宽泛的 `button` / `h2` / `input` 全局覆盖，特别不能泄漏到 iframe 业务画板。
4. **不要叠补丁**：在原组件声明附近修改；删除失效/冲突的旧规则。新增 `!important`、行内 `style=`、重复末尾“final refinements”需说明必要性并进行特异性检查。
5. **共享产品功能只改产品层**：UI 工具/画板编辑器的修改不应在每个用户 `vN` 中贴一份样式；运行时升级需遵守画布版本/分享兼容机制，不擅改历史业务代码。
6. **素材纪律**：优先使用仓库现有 SVG/Lucide 路径、图标尺寸与笔画，不引入新的图标包只为一个按钮。外部字体不可成为离线使用的唯一依赖；保留系统字体回退。
7. **行为与状态同步验证**：CSS/DOM 修改后必须实际检查交互，不接受只通过 `node --check` 就声称 UI 完成。涉及 canvas、分享、PRD 的修改跑对应项目测试，记录命令和结果。

## 7. AI 设计 Review → 修复闭环

每次新建或修改 **Prota 产品 UI**，实施者都必须执行以下顺序。用户说“这个 UI 不好看/不统一/按规范重审”时，直接从第 2 步开始，不需要再询问是否执行 Review。

1. **声明范围**：列出受影响的产品区域、文件、交互任务；判断是否为产品 UI、第三方外壳或业务 Demo。核对现有相邻界面和复用组件。
2. **独立 Review**：对照本规范逐项检查信息层级、布局、字体/间距、颜色/组件、交互状态、可访问性/响应式；**查实际渲染截图，不仅凭 CSS 猜测**。
3. **列问题与证据**：使用下表，给出具体文件/选择器/截图位置、实际表现、违反的规则、影响、建议修法；未观察到的现象不能说已复现。
4. **分级**：`P0` 功能不可用/数据丢失/核心操作被挡；`P1` 明显不一致、核心任务难找、可访问性或窄屏严重问题；`P2` 对齐、间距、文案、动效等精修。优先修 P0/P1，P2 同区域顺手处理。
5. **最小范围修复**：从共享 Token、共用组件或上层工具修，杜绝每个画板复制补丁。保留业务行为，补齐默认/hover/active/focus/disabled/loading/empty/error 等适用状态。
6. **复检和交付**：同尺寸对比前后截图、键盘与长文案检查；列出实际执行的测试、未测项及残余问题。P0/P1 未解决时不能写“已通过”。

Review 记录格式：

| 级别 | 区域/证据 | 违反条款 | 用户影响 | 修复动作 | 复检结果 |
| --- | --- | --- | --- | --- | --- |
| P1 | `path:selector` + 截图/复现 | §2.3 / §4 | 例：同级按钮尺寸不同 | 复用 36px 控件样式 | 待测/通过/失败 |

**七项判定**（每项 0=不合格、1=部分满足、2=满足）：①核心任务与信息层级 ②版式/留白 ③文字可读性 ④Token 与组件一致性 ⑤交互/状态闭环 ⑥响应式/键盘无障碍 ⑦样式隔离/版本与数据安全。目标 ≥12/14 且**无未解决 P0/P1**；分数只是辅助，不能代替事实与截图。

可直接交给 Codex / Claude Code / pi Agent 的提示：

> 请读取 `AGENTS.md`、`docs/prota-ui-guidelines.md` 和相关模块代码，对本次变更范围做一次严格的 Prota **产品 UI** Review。先列出可复现的 P0/P1/P2 问题（证据到文件/选择器与截图），再在不改变业务逻辑、历史版本和独立分享能力的前提下修复。复检 1440/1024/860 宽度及适用的窄屏、键盘与所有重要 UI 状态；给出问题清单、修复文件、前后对比、测试结果和剩余风险。不要把产品 UI 规范强加给用户生成的业务 Demo，也不要用新增 `!important` 掩盖旧样式冲突。

## 8. 推进顺序与治理

- **新增/重做页面**：从第一行代码就按本规范；不积累新的例外。
- **碰到旧模块**：先修本次触及的区域及其共享组件，不做无关的大规模“视觉翻新”。
- **全局清债**：按审计中的优先级先统一 Token 和按钮/输入/弹窗，再收敛重复 CSS，最后做细节视觉一致性；每阶段用截图与回归测试证明没有损坏。
- **更新规范**：发现规则不适用，应修改本文件并说明原因，而不是悄悄在新页面创建第四种标准。建议由项目维护者审核变更。
