# 终端模型与思考强度统一选择器 + 会话内「模型已切换」提示

## Context

当前 Composer 底部有两个独立入口：`#agentModelToggle`（实际列出的是 **Provider** 而非 Provider 下的具体模型）和 `#agentReasoningToggle`（思考强度菜单）。勘察确认《技术执行方案 v1.0》（~/Downloads/Prota-终端模型与思考强度统一选择器-技术执行方案.md）**尚未实施任何部分**，且存在如下真实缺陷：

- `activateProvider`（portal/shell.js:12583）网关调用失败不回滚；`handleSdkSetModel`（server/agent-server.mjs:5609）与 `ensureSessionAgent`（:3496）**先改 `session.providerConfig` 再调 Pi**，失败留下半提交状态。
- `set-provider` 不发任何事件；`set-model` 发 `session_ready` 但 UI 从不渲染；SSE 仅在任务运行中订阅，空闲切换的事件只能等下次 `/history`。
- 底部标签读的是**全局 active provider**（:14616），不是当前会话实际模型。
- 会话流中没有任何模型切换痕迹（用户截图需求）。Pi 自身 JSONL 已原生记录 `model_change`，但 Prota 时间线从未呈现。
- 用户友好名「GLM-5.3-Flash(个人套餐)」只存在于前端 Provider Store 的 `label`，`buildConfig()` 不上送，服务端只知道预设名。
- `session.runState.runId` 在任务结束后**不会清空**（:4062），空闲时 `emitEvent` 会把事件归入上一轮 run 分组。

**已确认的决策**：完整实施方案阶段 A–E；会话提示**仅覆盖模型/Provider 变化**（思考强度变化不进会话流，只同步底部入口）；**严格按原方案**保留刻度拖动与 bridge 补偿回滚/未同步保护态；在 **origin/main(805203a) 新建 worktree** 开发，流程图 WIP 不动。

## 整体数据流

```
Picker 点击 → shell.applyModelEffortSelection(req)
  → model-effort-transaction.apply()
     ① api.setSelection → POST /api/agent/session/:id/selection
        → applySessionSelection(): 守卫→校验→快照→改配置→piGateway.ensure→get_state 校验
          → 成功: revision++ / persist / emitEvent('session_selection_changed', runId:null)
          → 失败: 恢复快照 + 重建旧 Runtime（再失败→ selectionDesynced）
     ② bridge: store.applySelection(静默) → POST /api/agent-provider-config(expectedRevision)
        → 失败: 补偿 setSelection(old)；补偿失败→ 前端「未同步保护态」
     ③ commit: store/localStorage、agentEffectiveSelection、upsert event → 时间线分隔行
```

## 阶段 C：服务端单次选择事务 + 事件

**`server/agent-server.mjs`**
- `resolveProviderConfig`(1827)：接受并返回 `providerId`（实例 id）与客户端 `label`（trim、限长）；`sanitizeProviderConfig`(1863) 一并输出 → 自动进入 `providerSummary` 快照与 `/history`。
- `emitEvent`(1934)：支持 `options.runId` 显式覆盖（`undefined` 时沿用旧逻辑），选择事件传 `runId: null`。
- 新增 `getSessionSelection(session)` → `{providerId, provider, label, model, configuredReasoning, effectiveReasoning, source:'provider-default'|'session-override', revision}`；`effectiveReasoning`：`engineInfo.thinkingTarget` 匹配当前身份时取 `engineInfo.thinkingLevel`。`handleHistory`(5526) 与所有 `session_ready` payload 附带 `selection`。
- 新增 `applySessionSelection(session, {providerConfig, expectedSelectionRevision, requestId, source})`：
  1. 守卫 `activeRun/_runStarting/_piOperation/manager.get(id)?.busy` → 409；占用 `_piOperation='selection'`；requestId 去重（session 内最近 N 条）；revision 不符 → 409。
  2. `resolveProviderConfig` + 用共享的 `portal/agent/reasoning.js getReasoningCapability` 二次校验强度 → 400。
  3. 快照 `prev = {providerConfig, engineInfo.thinkingLevel/thinkingTarget, selectionRevision}`。
  4. 写入候选配置，清除会话 thinking 覆盖，`await piGateway.ensure(session)`，再 `rpc.request('get_state')` 比对 model，不符视为失败。
  5. 成功：`selectionRevision++`、`persistSession`、`emitEvent('session_selection_changed', {from, to, changes:['model'|'provider'|'reasoning'], source, revision}, {runId:null})`；返回 `{ok, selectionRevision, selection, event}`。
  6. 失败：恢复 `prev` 并 `piGateway.ensure` 重建旧 Runtime；重建也失败 → `session.selectionDesynced=true` 持久化，502 带 `desynced:true`。错误文本脱敏（无 apiKey/路径/堆栈）。
  7. finally 释放 `_piOperation`。
- 新路由 `POST /api/agent/session/:id/selection` → `handleSdkSetSelection`；`POST .../selection/recover` 用当前持久化配置重新 ensure 并清除 desynced。
- `handleSdkSetModel`(5601)、`handleSdkSetProvider`(5650) 改为委托 `applySessionSelection`（保留响应形状，获得回滚与事件）；`set-model` 的 `session_ready` 改 `persist:false`，消除空的 session 分组。
- `handlePiSessionCommand`(5803) `thinking` 成功后 emit `session_selection_changed`（`changes:['reasoning']`, `source:'session-override'`）。
- `handleSdkPrompt`/run 启动：`selectionDesynced` → 409 `code:'SELECTION_DESYNCED'`。

**`server/pi/gateway-adapter.mjs`**：第 45、227 行 `thinkingTarget` 身份加强为 `[providerId||provider, baseURL, model]`；`sessionCommand('thinking')` 返回 Pi `get_state().thinkingLevel`。

**测试**：新建 `tests/pi-selection.test.mjs`（参照 `tests/pi-sessions.test.mjs` 启真实 Pi）：同 Provider 切换复用进程且 `get_state.model` 正确；跨 Provider 重建保持 piSessionId；prompt 中 409；revision 冲突 409；非法强度 400；目录外模型强制失败 → 旧配置保留、旧 Runtime 可用、无事件；`/thinking` 后事件为 reasoning-only，再切模型时覆盖被清除；事件以 `runId:null` 持久化到 `<workspace>/data/agent-sessions/<id>.json`。

## 会话内「模型已切换」提示（用户截��需求）

- **数据**：即上面的 `session_selection_changed` 事件（持久化、`runId:null`）。`from/to` 带 `{providerId, provider, label, model}` 快照，保证改名/删除 Provider 后历史文案不变。
- **渲染（`portal/shell.js`）**：`renderAgentTimelineGroup`(16733) 在用户行之前，对分组内 `changes` 含 `model`/`provider` 的事件输出 `renderAgentSelectionNotice(event)`；`renderAgentAssistantTurn`(15744) 跳过该类型（与 `session_ready` 同列）。**仅 `reasoning` 变化不渲染**。若事件之前时间线没有任何 `run_started`（空会话），不渲染。
- **标记**：`<div class="agent-selection-notice" data-event-id title="完整 label · model → label · model"><span class="…__line"></span><span class="…__text"><svg ⇄/> 模型已切换 A → B</span><span class="…__line"></span></div>`，A/B 由 `formatSelectionDisplay` 生成（得到「GLM-5.3-Flash(个人套餐) → magpie/auto/deepseek-v4.1-flash」）。单行、无副标题（遵守 AGENTS.md §9）。
- **样式（`shell.css`，置于 6043 时间线令牌附近）**：`display:grid; grid-template-columns:1fr auto 1fr; gap:10px`；线 `rgba(148,163,184,0.12)`（同 `.agent-timeline__details`）；文字 `#64748b` 0.72rem，模型名 `#94a3b8`；适配 Agent 面板深色调。
- **时效**：成功响应里的 `event` 立即 upsert（空闲时无 SSE）；SSE 分支同样处理；刷新后由 `/history.timeline` 还原；分组逻辑 `buildAgentTimelineGroups`(15096) 按 `runId||'session'` 自动把它放在两轮对话之间，notice-only 分组永不 active，无需改 `getAgentTimelineChildKey`。
- **测试**：新建 `tests/agent-selection-notice.browser.mjs`：有历史的会话切模型 → 出现分隔行且文案正确；刷新仍在；空会话不出现；仅改强度不出现；`/model`、`/provider` 命令同样出现；显示名三种规则。
